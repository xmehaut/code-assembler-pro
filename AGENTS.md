# Part 1 — Using this tool

## What it does

`code-assembler-pro` consolidates a codebase into a single structured
Markdown file, optimized for LLM ingestion — pasting an entire project into
a chat, feeding it to a context window, or archiving a reviewable snapshot.
It is an alternative to tools like Repomix.

```bash
pip install code-assembler-pro
code-assembler src/ --ext .py --output codebase.md
```

## Recognizing a file this tool produced

Every generated file opens with a small YAML frontmatter block — the very
first thing in the file, so it's visible even if you only read the start of
a large document:

```yaml
---
type: source-bundle
generator: code-assembler-pro
generator_version: "4.7.0"
rebuild: "pip install code-assembler-pro && code-assembler --rebuild <this-file> --output-dir <dir>"
...
---
```

`type: source-bundle` plus a `rebuild:` command telling you exactly what to
run is the fastest signal — you don't need to scroll to the end of the file
to confirm what you're looking at or how to act on it. A hidden
`<!-- CODE_ASSEMBLER_METADATA ... -->` JSON block at the true end of the
file is what `--rebuild` actually parses; the frontmatter is there so you
don't have to go looking for it.

If the frontmatter also has a `module:` field, the file is one output of a
multi-module (monorepo) batch — see the `modules` section below for what
that implies.

If you (an agent) receive a `.md` file generated by code-assembler-pro, use
`--rebuild` instead of parsing the markdown yourself. The rebuilder already
handles tricky, non-obvious cases via regression tests: nested code fences
inside `.md` files, files sharing the same name at different paths, prose
headers that merely resemble filenames, a file's own content that happens
to mention `<!-- CODE_ASSEMBLER_METADATA -->` or `[TRUNCATED]` in prose
(both found by running this tool on its own source, where the docs
literally describe these markers), and a directory's README content
injected between two files. Manual regex parsing risks reconstructing the
project incorrectly on any of these.

## Describing what a file contains

Two optional fields, useful when you're the one generating a snapshot
(not just consuming one):

- **`--description "..."`** (CLI) or `"description"` (JSON config) — a
  free-text line embedded in the frontmatter. Omitted entirely if not set.
- **`modules`** (JSON config only) — assembles several sub-projects of a
  monorepo in one pass, one output file per module, instead of one
  invocation per sub-project run by hand:
  ```json
  {
    "extensions": [".py"],
    "output": "codebase.md",
    "modules": {
      "shared": { "paths": ["./libs/core"] },
      "api":    { "paths": ["./api"], "depends_on": ["shared"],
                  "description": "REST API" }
    }
  }
  ```
  Every module's frontmatter gets a `siblings` list (the other modules'
  file name, description, token count) and its own `depends_on` — so if
  you land on `codebase_api.md`, you know `codebase_shared.md` exists,
  what it's for, and roughly how big it is, without opening it. `--since`
  and CLI overrides are rejected outright on a `modules` config rather
  than silently guessed at — see *Known pitfalls* below if you're touching
  this code path.

## What makes it different

**Modular tree-sitter parsers, not a monolithic dependency.** Optional code
compression (`--compress`) reduces files to signatures and docstrings only.
Python is supported out of the box via stdlib `ast` (no extra install).
Other languages use individual tree-sitter packages, installed via named
extras instead of one heavy all-languages bundle:

```bash
pip install "code-assembler-pro[compress-web]"      # JS + TS
pip install "code-assembler-pro[compress-systems]"  # Rust + Go + C + C++
pip install "code-assembler-pro[compress-js]"        # a single language
pip install "code-assembler-pro[compress-all]"       # everything
```

**Reversible: it can rebuild a project from its own output.** Unlike most
"dump codebase to text" tools, the generated Markdown embeds a hidden
metadata block that makes the snapshot reconstructable:

```bash
code-assembler --rebuild snapshot.md --output-dir ./restored
```

Other useful flags: `--since snapshot.md` for incremental/delta updates,
`--config file.json` for repeatable configurations, `--clip` to copy
straight to the clipboard, `--dry-run` (with `--rebuild`) to preview without
writing to disk.

# Part 2 — Contributing to this repo

## Quick start

```bash
pytest tests/
```

Don't rely on a specific test count here — it grows with every feature, and
any number written into this file would be stale within a release or two.
Expect everything to pass with exactly **one skip**, which is **expected**:
it corresponds to a tree-sitter test that only runs when the optional
tree-sitter packages are installed. Do not try to "fix" it or make it
mandatory.

If you're asked to add a feature or fix a bug, default to preserving the two
properties described in Part 1 — modular per-language parsers and
rebuild reversibility — unless the user explicitly asks to change them.

If you're touching the public API surface (`assemble_codebase`,
`assemble_from_config`, `assemble_modules`, `CodebaseRebuilder`), see
`ROADMAP.md` for the current direction before assuming one — an earlier
revision of this file asserted a specific "v5.x: expose this as a Claude
Skill / MCP tool" plan here; that framing turned out to be premature (the
trigger for an agent to invoke this proactively is weak — see the design
discussion referenced in `ROADMAP.md`) and has since been narrowed
considerably. `ROADMAP.md` is the current source of truth on this, not this
file — don't let the two drift again by restating a roadmap decision here.

## Known pitfalls / rules to follow

**CLI + `--config`: overrides must be forwarded explicitly — except for a
`modules` config, where they're rejected outright.**
The `--config file.json` + additional CLI flags pattern (`--compress`,
`--since`, `--description`) is fragile by design: a CLI flag does NOT
automatically apply on top of the JSON. Any new option must be explicitly
passed through to `assemble_from_config`, with the CLI value taking
precedence over the JSON value. This is already the case for `--compress`,
`--since`, and `--description`; if you add a CLI option, verify that this
forwarding exists for it too.
The one deliberate exception: if the config contains a `"modules"` key,
`assemble_from_config` raises instead of forwarding *any* CLI override —
there's no single module a flag like `--compress` should apply to, and
guessing would be worse than refusing. If you're "fixing" what looks like
missing forwarding for `--since` or a CLI override inside
`assemble_modules()`/the `"modules" in config_data` branch, stop — that's
intentional, not an oversight. See `MODULES_SPEC.md` §11.

**`re.sub()` with a computed string replacement: pass a function, not the
string.** `assemble_modules()`'s frontmatter-patching phase regenerates a
module's frontmatter once the whole batch is known, then splices it in
with `re.sub(pattern, replacement, content)`. When `replacement` is a
*string*, `re.sub` interprets backslashes in it as backreferences (`\1`,
`\g<name>`, ...) — and `json.dumps()` (used to escape `description` safely
for YAML) escapes any non-ASCII character as `\uXXXX`, which isn't a valid
backreference and raises `bad escape \u`. A description containing so much
as an em-dash was enough to crash the whole batch. Fixed by passing
`lambda _match: replacement_string` instead. If you add another spot that
splices generated text into a document via `re.sub`, use the same pattern —
don't reintroduce a bare string replacement.

**Self-referential documents: use the *last* match, never the first, for
anything that's supposed to be unique.** Two real bugs, both found only by
running this tool on its own source tree (where the documentation
naturally describes the tool's own markers in prose):
- `_extract_metadata` (rebuilder.py) used to take `re.search()`'s first
  match. `core.py` always appends the real metadata block after all file
  content, so it's structurally guaranteed to be the *last* match, not
  necessarily the only one — any file whose prose describes this feature
  (a CHANGELOG entry reading `` "...`<!-- CODE_ASSEMBLER_METADATA ... -->`"... ``)
  creates an earlier, non-JSON decoy.
- The truncation-warning check used to do a bare `"[TRUNCATED]" in content`
  substring search. `core.py`, `rebuilder.py`, and the test suite all
  legitimately contain that string without ever being truncated. Now
  anchored on the real marker's distinctive final line, matched only as a
  suffix.
If you add another "does this special marker appear" check, ask whether the
codebase being analyzed could itself be this one (or could describe this
tool) — if so, anchor on structure (last match, suffix, whatever the real
marker's actual invariant is), not a bare substring search anywhere in the
document.

**Tree-sitter is an optional dependency, never mandatory.**
Compression (`--compress`) relies on stdlib `ast` for Python (always
available) and on individual per-language tree-sitter packages for everything
else (`tree-sitter-javascript`, `tree-sitter-rust`, etc.). If a tree-sitter
parser is missing, `compress()` must return the original content without
raising an exception — never let the assembly crash because of a missing
parser.

**`_detect_language` (formatters.py): extension first, filename as
fallback.** Language detection for syntax highlighting first tries the
extension via `LANGUAGE_MAP`, then falls back to a list of exact filenames
(`Dockerfile`, `Makefile`, `Procfile`, `.env*`, `CMakeLists.txt`). If you
modify this function, rerun `tests/test_formats.py` to verify these special
cases are still covered.

**`normalize_path` (utils.py): no resolution against CWD.**
Normalization converts to POSIX lowercase but deliberately never resolves
the path against the current working directory, in order to remain
independent of the execution environment. Do not replace it with
`Path.resolve()` or equivalent.

**`os.path.commonpath`: keep the Windows multi-drive fallback.**
On Windows, `commonpath` raises a `ValueError` if the analyzed paths are on
different drive letters (`C:\` and `D:\`). The current fallback falls back
to `os.getcwd()` — keep this if you touch `analyzers.py`.

**`--dry-run` : ni écriture de fichiers, ni création du dossier de sortie.**
`CodebaseRebuilder.rebuild()` n'appelle `output_dir.mkdir()` que si
`dry_run` est `False`. En mode dry-run, chaque fichier déclenche un simple
`print("[DRY-RUN] Would create: ...")` et incrémente le compteur, sans
aucune opération d'I/O — le dossier `output_dir` ne doit pas exister à la
fin. Si vous ajoutez une étape au pipeline de rebuild (ex. écriture d'un
rapport, copie d'assets), placez-la après la vérification `if self.dry_run`
et assurez-vous qu'elle ne déclenche pas de création de répertoire ou de
fichier. Couvert par `test_dry_run` dans `test_rebuild.py`.

**Metadata paths are relative to the CWD, not the assembled root.**
`generate_metadata_block()` records each file's path relative to
`os.getcwd()` at assembly time, not to any common root of the paths being
assembled. Running from a different directory than the analyzed tree
produces manifest entries like `"../../../../AppData/Local/Temp/.../file.py"`
— harmless (a full run and a later `--since` run against it still agree,
since both compute paths the same way), but don't assume the manifest's
keys are clean relative paths from the project root if you build something
that reads it directly.

## Testing conventions

A fixed bug = a regression test added to `tests/test_robustness.py` (or, for
rebuilder-specific regressions, `tests/test_rebuild.py`'s
`TestRebuildRegressions` class — both patterns exist in the suite, pick
whichever the bug is closer to), named in a way that explicitly identifies
the bug it covers (not a generic name like `test_edge_case_1`). The test's
docstring should explain the scenario that caused the bug, not just what it
checks.

Encoding: always use explicit `encoding='utf-8'` on file operations, with no
exceptions. This is already systematic in the existing code — keep it that
way.

## Known limitations — do not oversell

- Compression on complex Python patterns (nested decorators, dataclasses,
  metaclasses) is not yet covered by dedicated tests. Treat `--compress` as
  "best-effort" on these cases, not as guaranteed robust, until real-world
  feedback or tests confirm it.
- Individual tree-sitter parsers (0.21+ API) are not all equally mature
  across languages. Do not assume uniform compression quality between
  Python (ast, reliable) and tree-sitter-based languages.
- `assemble_modules()`'s two-phase design (assemble each module, then patch
  its frontmatter once the whole batch is known) writes each output file
  twice rather than deferring the write until everything is known — a
  pragmatic choice over refactoring `assemble_codebase()` into separate
  "compute" and "write" steps. No user-visible difference today, but don't
  assume the write happens exactly once if you're reasoning about I/O
  ordering or file-system side effects in this path. See `MODULES_SPEC.md`
  §9's implementation note.
